# Chat groups in the Desktop custom build

Base: `4617040c7b650b37d599bdaa08d3790572c19ae8` (Desktop `1.54.0`). This is a local Desktop customization, not a goose session schema migration.

## Use

Open the sidebar. The **+** immediately right of **Chats** creates a named, flat group; type a name and press Enter or click away (Escape cancels). Drag a recent chat onto a group to assign it; drag it onto **Ungrouped** to unassign. Double-click a group name to rename it; use the trash icon to delete a group after confirmation. Deleting a group unassigns its chats; it never deletes session history. Empty groups remain visible. The sidebar shows the most recent 25 user/scheduled sessions, so older sessions can have saved assignments but won't appear here until they enter this recent list. Chat History displays the same flat groups across its paginated history, with dates inside each expandable group and an Ungrouped section. Drag a history card into another group or Ungrouped to assign even an older session; the sidebar reflects changes for sessions in its recent list. History preserves the separate Scheduled Jobs section and its existing search/ACP filter. Empty groups stay visible as drop targets. Group names, membership, and order are shared through the existing renderer storage key; changes in one window update the other windows.

Group names and session ID → group ID memberships are stored as `goose.desktop.chatGroups.v1` in Electron's persistent `persist:goose` renderer localStorage. They survive normal app restart for the same Desktop profile, but are not portable to another profile/device and are not part of ACP/CLI server session metadata. Clear-site-data/profile reset removes them. Concurrent windows share the storage partition and receive `storage` updates; simultaneous edits are last-writer-wins. A custom build reusing the stock app profile also reuses these group settings; isolate the custom distribution's userData/partition before running it alongside an installed stock goose app. Storage failures and profile migration are not handled by this MVP. New UI labels are registered in all locale catalogs with English fallback text; translations remain to be supplied. Assignments for deleted sessions remain inert until the group is deleted; this avoids accidentally losing saved assignments while sessions fall outside the 25 most recent results.

## Directory versus group

ACP `SessionInfo.cwd`/Desktop `SessionListItem.workingDir` is the working directory. Historically the sidebar generated _project headings_ from that path (`projectSessions.ts`); those headings have been replaced in this sidebar with _custom groups_, which are independent of paths. Group assignment only updates renderer UI state, never calls an ACP session update, directory chooser, or `working_dir` setter. A resumed chat still uses its original directory. The session tooltip continues to display the actual directory. Project grouping utility/test remain available, but the navigation sidebar no longer uses it.

## Agent interaction (deferred)

**There is no agent-callable group move in this build.** A prompt such as “move this chat to Work” cannot currently perform the move: the model's tools (for example `crates/goose/src/agents/platform_extensions/developer/mod.rs`) execute in the goose agent/server and cannot address a particular Electron window's renderer localStorage. ACP `session/list` supplies session IDs, title and `cwd`; it has no group metadata or group assignment operation. Telling the agent to edit the goose SQLite database or to treat `cwd`/project ID as a group is **not** safe and will not update this sidebar. Do not use a shell script to write the Chromium storage files.

A tool-result platform notification is **not** sufficient for a reliable move. `ToolCallContext.session_id` identifies the requesting chat, and `result_with_platform_notification` can attach a group name and session ID to a tool result. However, `ops_toolcalling.rs` emits that notification separately from the result; the ACP adapter forwards it as an in-progress `tool_call_update`, and `chatNotifications.ts` dispatches it to renderer listeners without a reply channel. The model may receive the tool's result when no Desktop window received the notification, when the current session is no longer active, when the requested name is missing or ambiguous, or when localStorage fails. A renderer warning/toast alone would not tell the agent the move failed. Do not present dispatch as successful assignment.

The smallest safe follow-up for this localStorage MVP is a **request/reply** Desktop-only ACP bridge (requiring an explicit protocol/design decision), not a fire-and-forget platform event:

1. Expose a scoped agent tool that takes only a target group name; obtain the current session ID from `ToolCallContext`, not a model-supplied ID. Route a correlated request to the Desktop window owning that active session, with timeout and disconnect errors. Do not offer this tool in CLI/headless sessions unless it reports that Desktop assignment is unavailable.
2. In that renderer, check that the request session ID matches the current active session **and** an existing recent session. Resolve a trimmed, uniquely matching group name in the current localStorage state; treat `Ungrouped` as an explicit unassign target, reject empty/unknown/duplicate names and the reserved-name collision, and never alter `cwd` or project IDs. Prefer an explicit group ID in the acknowledgement to avoid a second lookup.
3. Use the same state transitions and persistence key as sidebar drag/drop; acknowledge success **only after** the localStorage write succeeds. Return a structured failure for missing/ambiguous group, missing session, stale window, denied access, or write error. The tool's result should be based on that acknowledgement, not on delivery of the request. Keep the existing `storage` event sync for other windows, documenting its last-writer-wins concurrency limit. Verify renderer teardown, multiple windows, timeout/retry and result-vs-notification ordering in tests.

A durable shared backend group service with atomic writes, authenticated session/group membership and broadcasts to all windows would supersede the localStorage bridge if reliable multi-window conflict resolution or non-Desktop support is required. Neither approach is implemented in this build; for now use drag and drop. No hidden keyboard/menu move action was added.
